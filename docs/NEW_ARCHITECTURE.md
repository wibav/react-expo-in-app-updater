# New Architecture status and maintenance notes

Notes for maintainers. Last reviewed: 2026-11-12, when the native module was
migrated from a legacy bridge module to a TurboModule (1.0.0).

## TL;DR

- The library is a **TurboModule**. Its native interface is generated by React
  Native codegen from `src/NativeReactExpoInAppUpdater.ts`, so it no longer
  depends on React Native's compatibility path for legacy modules.
- It requires the **New Architecture**. Apps on the legacy architecture must
  stay on `0.3.x`.
- The JavaScript API (`checkForUpdate`, `UpdateFlow`) and every error code and
  message are the same as in `0.3.x`, and tests now guard them.
- Error **messages** are part of the public contract: at least one consumer
  filters on them. Treat changes to them as breaking.

## Architecture

| Layer   | Implementation | Notes |
| ------- | -------------- | ----- |
| Spec    | `src/NativeReactExpoInAppUpdater.ts` (`TurboModuleRegistry.get<Spec>`) | Source for codegen (`codegenConfig` in `package.json`, spec name `ReactExpoInAppUpdaterSpec`) |
| JS      | `src/index.tsx` | Validates the flow and throws a linking error when the module is missing |
| Android | `ReactExpoInAppUpdaterModule` extends the generated `NativeReactExpoInAppUpdaterSpec`; `ReactExpoInAppUpdaterPackage` is a `BaseReactPackage` that registers it with `isTurboModule = true` | `android/build.gradle` always applies `com.facebook.react`, which runs codegen |
| iOS     | `ios/ReactExpoInAppUpdater.mm` conforms to the generated `NativeReactExpoInAppUpdaterSpec` protocol and forwards to the Swift class `ReactExpoInAppUpdaterImpl` in `ios/ReactExpoInAppUpdater.swift` | Codegen runs through `install_modules_dependencies` in the podspec |

Things that are easy to break:

- The method signature must match in four places: the spec, the Kotlin
  `override`, the Objective-C++ method and the Swift `@objc(checkForUpdate:resolve:reject:)`.
- `ios/ReactExpoInAppUpdater.h` imports C++ headers, so the podspec keeps it
  private (`private_header_files`); otherwise Swift cannot build the module.
- The `.mm` imports `StoreKit` before the Swift-generated header, which
  references `SKStoreProductViewControllerDelegate`.
- `ReactModuleInfo` is built with positional arguments because its parameter
  names changed between React Native versions (`_name` in 0.76, `name` later).

## Verified

With the `example/` app (React Native 0.76.5, New Architecture, bridgeless):

- ✅ `yarn lint`, `yarn typecheck`, `yarn test`, `yarn prepare`.
- ✅ Android debug build compiles, including codegen.
- ✅ iOS debug build compiles (simulator, Xcode 27).
- ✅ iOS runtime (iPhone simulator, iOS 26.5): `checkForUpdate` reaches the
  Swift code and rejects with `FETCH_ERROR` / `App not found in App Store.
  Bundle ID: com.reactexpoinappupdater.example`, as expected for an unpublished
  bundle ID.
- ✅ Android runtime (Pixel emulator, API 34, sideloaded debug APK):
  `checkForUpdate` reaches the Kotlin code and rejects with
  `UPDATE_CHECK_FAILED`, passing through Play Core's `Install Error(-6)`
  message, as expected for an app not installed from Play.

Not yet verified:

- A consumer app on React Native 0.88 / Expo SDK 58 with this version.
- An actual update flow. That needs a build installed through a Play Store
  internal testing track (Android) and a bundle ID published in the App Store
  (iOS). The Play In-App Updates API does not work for sideloaded APKs.

The example app on React Native 0.76 crashes at launch on iOS 27 because its
`AppDelegate` does not adopt the UIScene lifecycle. That is a limitation of the
example's React Native version, not of this module; upgrading the example app
fixes it.

## Error contract

Consumers match on what this module rejects with, so both codes and messages
should be treated as public API.

### Codes and messages currently produced

| Code                  | Message                                       | Source                               |
| --------------------- | --------------------------------------------- | ------------------------------------ |
| `NO_ACTIVITY`         | `No current activity`                         | Android                              |
| `INVALID_TYPE`        | `Update type must be 'FLEXIBLE' or 'IMMEDIATE'` | Android                            |
| `NOT_ALLOWED`         | `Flexible update type not allowed`            | Android                              |
| `NOT_ALLOWED`         | `Immediate update type not allowed`           | Android                              |
| `UPDATE_CANCELLED`    | `User cancelled the update`                   | Android                              |
| `UPDATE_CHECK_FAILED` | Passthrough of the Play Core exception message | Android |
| `FETCH_ERROR`         | `App not found in App Store. Bundle ID: …`    | iOS (wraps an `NSError` with code `404`) |

`UPDATE_CHECK_FAILED` forwards `e.localizedMessage` from Play Core unchanged. One
message seen in the wild through it is `Play Store app is either not installed or
not the official version`, which is a Play Core string, not one of ours.

### Known consumer that depends on the messages

The Sima / Open Matic app (`src/utils/sentryRuido.js`) suppresses expected
environment conditions before reporting to Sentry, matching these strings:

```
App not found in App Store
User cancelled the update
Immediate update type not allowed
Play Store app is either not installed
No current activity
```

Rewording any of them makes that app start reporting them as errors. Before
changing a message, either keep the old text as a prefix or coordinate the
change. The robust fix lives on the consumer side: match on `error.code`, which
is stable, instead of on the message.
